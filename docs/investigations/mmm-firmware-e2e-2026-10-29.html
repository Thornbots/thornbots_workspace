Execution path

The MCB emulator already runs real firmware; this test uses the explicit hosted backend (compiled SentryControl with hardware inputs), not a protocol reimplementation. Two PTYs and a fault relay connect it to the real bridge. auto.launch.py real_hardware:=false starts mmm but omits the bridge, so the suite starts it separately. Gazebo supplies sensors; the real mapping stack resets SLAM and saves. The one-command suite uses a private hosted socket for start/save and DBUS joystick inputs. Unit checks show the hardware source graph excludes hosted/ and that preprocessing its control header without MCB_HOSTED exposes no interface. No UART field changed.

Measurements and scenarios

Link latency is far inside the peers' 500 ms retry budgets.
With 87.87 Hz POSE and 9.65 Hz REF_SYS load, observer round-trip maxima for 0/2/4 were 10.260/5.247/5.188 ms; firmware-origin 1/3 reached 5.175/6.711 ms; setup failure 6, 0.328 ms. Main had 16 probes and 16 replies, no loss. Other runs inject faults, so this is not a claimed zero-loss link.
Hosted loop timing says nothing about the STM32.
1.032 ms active vs 1.040 ms inactive period (including fixture pacing); work 45.47 vs 47.66 µs per tick; nominal firmware time advances 1 ms per iteration.
Backpressure drops telemetry but does not corrupt state.
50 simulated seconds with the reader stalled: 43,539 failed UART writes; the pending start was delivered after draining; 721 telemetry frames survived of about 5,100 nominal. One truncated frame gave one CRC16 error and lost the first Ready echo; one repeated Ready request recovered it, with no extra state change. This exposes the hosted PTY's partial-write behaviour.
Every injected loss and corruption recovers with bounded traffic.
One frame dropped and one corrupted per direction for each of 1/2/3/4 (eight and eight) and for 1/6 in setup failure (four and four). All exchanges complete, and the quiet observation finds no continuing echo loop. Full-flow frame totals (C→J / J→C): 1: 8/6, 2: 10/12, 3: 12/8, 4: 8/10; setup-failure 6: 4/6. The firmware restart session has exactly eight state changes.
Bridge and firmware restarts recover.
Bridge restart in Ready (start left held) and in Mapping during a retrying save both recover. Firmware restart to Main with Jetson alive, then start again after the odd-request quiet gap, creates a distinct session directory and reaches Ready.
Exactly one ping_to_mcb publisher exists.
Named mmm in the launched auto graph; the test only subscribes.
State restrictions hold.
Setup/Done: zero translation. Ready and Mapping clamp diagonal full stick to 0.400000 m/s; Gazebo measured 0.39962 (Ready) and 0.40069 (Mapping). Active states have zero indexer and flywheel CAN commands, no shots, level pitch and a forward head target. Ready's beep period is 1,000 ms; the green LED is inferred from Ready state because GPIO output is not exposed.
A failed final save recovers, then a retry validates.
A pre-existing snapshot directory forces the save to fail: Done goes through 4 to Mapping, then Ready. The next save reaches Done with validated:true and nonempty posegraph/data/PGM/YAML/boot metadata. Non-mapping setup forces Setup through 6 to Done.

Corrections and limits

  • Early runs caught test defects: saving on the Mac bind mount failed in std::filesystem::copy_file (final runs use Linux $HOME); short departure could regain Ready before the intended save (now requires over 0.4 m observed departure and return); the return controller needed chassis heading in addition to the heading-fixed root transform. A localization test failed service discovery on its first run, and a new file needed the repository's Apache header. The fake-MCB integration left its known Gazebo child; only that task-created process was terminated.
  • The sim applies firmware velocity setpoints to Gazebo's velocity controller: it verifies command restrictions and observed translation, not the calibrated CAN motor plant. Head assertions observe the firmware target, not physical gimbal tracking; the beep check covers the real timer, not acoustics.
  • Still requiring robot acceptance: board scheduling, physical drive/head, GPIO and buzzer hardware, robot storage, field mapping, power-loss durability. The hook exclusion is a source-graph/preprocessor check; no new ARM build or Renode MMM run is claimed.
